# ADR-002: Templates oficiais Cloudflare + monorepo com dois Workers

**Status:** Accepted
**Date:** 2026-09-23
**Deciders:** usuário (owner)

## Context
O usuário exige templates Cloudflare como base para integrar stacks diferentes (blog editorial e agente com container). O Estágio 0 confirmou: C3 gera Astro+Starlight com adapter; o template `cloudflare/sandbox-sdk/examples/claude-code` entrega Worker+Container com isolamento de credencial. O spike 4a mostrou que Starlight 0.42 + `@astrojs/cloudflare` 14.3.3 falha no build (bug upstream `satteri`), enquanto o Starlight estático builda.

## Decision
Monorepo npm workspaces com `apps/blog` (Starlight estático + Worker mínimo de borda com Static Assets) e `apps/agente` (template claude-code do Sandbox SDK adaptado para o Agent SDK). Comunicação por **service binding**. Deploy de cada app por Workers Builds (root directory por app).

## Options Considered

### Option A: Blog estático + Worker de borda próprio (escolhida)
| Dimension | Assessment |
|---|---|
| Complexity | Low |
| Cost | Assets grátis; Worker só em `/api/*` |
| Scalability | Edge |
| Team familiarity | Alta (config Cloudflare padrão) |

**Pros:** contorna o bug do adapter; nenhuma SSR; custo zero de leitura. **Cons:** ~30 linhas próprias no `worker.ts`.

### Option B: C3 Astro + adapter Cloudflare (SSR/hybrid)
**Pros:** endpoint `/api` como rota Astro. **Cons:** build falha hoje (Starlight 0.42 × adapter 14.3.3).

### Option C: Um Worker único com Sandbox + assets
**Pros:** um deploy. **Cons:** blog passa a depender do plano pago e do container para existir; acopla falhas.

## Trade-off Analysis
Separar leitura (grátis, estável) de agente (pago, mais frágil) protege o blog. O custo é um Worker de borda mínimo, menor que manter workaround de bundling.

## Consequences
- Mais fácil: blog nunca cai por causa do agente; atualizar cada app independentemente.
- Mais difícil: dois projetos no Workers Builds.
- Revisitar: voltar ao adapter quando o bug upstream for corrigido, se trouxer ganho.
